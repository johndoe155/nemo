You are building a **standalone Card Shop** for "The Nemoverse," a Vite +

```ts
export type Rarity = 'common' | 'rare' | 'epic' | 'legendary' | 'secret';


export const RARITY: Record<Rarity, { label: string; color: string; weight: number; tier: number; note: string }>;
// common #c8cfe0 · rare #3fe8ff · epic #8a4dff · legendary #ffc857 · secret #ff3d9a

  id: number; code: string; name: string; world: string; lore: string;

  status: 'sold-out' | 'live' | 'upcoming' | 'encrypted' | 'secret';
  rarity: Rarity; supply: number; minted: number; price: number; // ETH on Base
  palette: [string, string]; image: string; tags: string[]; variant?: string;
}
```
These `Universe` records ARE "the cards" in this product — the numbered,
artist-commissioned collectibles (U-001…U-009 today). The existing `Store`
section (`Product` type: sku/name/kind/price/image/gated/note) sells
*physical merch* and is a separate, much smaller thing you are not replacing.
The Card Shop you're building is the dedicated, full-featured marketplace for
the `Universe` cards themselves — something the current site only gives a
420vh scroll-jacked teaser rail for, with no dedicated buy flow, filtering-only
browse, and no cart. `RARITY[rarity].weight` also implies a pull-odds context
(see `sections/pulls/`) — you don't need to replicate the gacha mechanic, just
be aware price/rarity/supply/minted already carry real meaning.


**Image pipeline:** JPG originals in `public/art/` are pre-processed by
`scripts/generate-art-variants.sh` into AVIF renditions at 540/840/full width
plus an inline 24px WebP LQIP, catalogued in `src/lib/art-variants.ts`.
`CardImage.tsx` serves them through `<picture>` + `sizes`, fades the bitmap in
over a blurred LQIP placeholder on load, and never causes layout shift.
Replicate this *pattern* (responsive `<picture>`, blur-up placeholder,
`loading="lazy"` except above-the-fold, `fetchpriority`) using whatever
source art you generate or placeholder for the shop.


**Motion contract:** framer-motion owns `transform` on interactive/tilting
elements; stylesheet-authored motion uses the independent `translate` /
`rotate` / `scale` properties so the two never fight. Card hover uses spring
physics (tilt + lift + parallax on the art layer + a stronger counter-move on
badges), never a plain CSS `transform: scale()` hover. Every animated thing
respects `prefers-reduced-motion` — collapse springs to instant/opacity-only
transitions, never just remove `transition` and leave a snap.


**Accessibility contract already in place:** skip link to main content,
cards are `role="button"` with `tabIndex`, `aria-haspopup="dialog"`,
`aria-labelledby`, and full `Enter`/`Space` keyboard activation; visually
hidden (`.vh`) text backs every icon-only control.

## 3. Phase 2 — Build the Card Shop


### 3.1 What it is
A dedicated marketplace page for browsing and acquiring Nemoverse Universe
cards: grid/list of cards, rich filtering and sorting, a detail view per
card, a cart/checkout stub, and holder-gated pricing — everything the
current embedded `Store` section and the scroll-jacked `Nemoverse` rail
don't give the collector today.


### 3.2 Required features
- **Catalog grid** of card entities (reuse the `Universe` shape). Responsive:
  1 column mobile → up to 4–5 columns desktop, no layout shift on image load.
- **Filtering**: by rarity, by status (`live` / `upcoming` / `sold-out` /
  `secret` / `encrypted`), by tag.
- **Sorting**: price (asc/desc), rarity (tier), release date, "most minted".
- **Search** by name/code/artist, debounced, no layout jank.
- **Card detail** (modal or route — your call, but must be deep-linkable via
  URL so it survives a refresh/share): lore, artist credit + quote, supply /
  minted progress, rarity badge, price, palette swatch, buy/mint CTA.
- **Holder-gated pricing**: mirror the existing pattern — a mock
  `useWallet()` hook that toggles a "HOLDER −25%" price state and unlocks
  gated cards, with a clear `// TODO: replace with real wallet connect`
  marker. Do not build real Web3 wallet integration.
- **Cart / checkout stub**: add-to-cart, cart drawer or page, quantity,
  running total, a clearly-labeled "demo checkout — no real payment" CTA.
  Toast/snackbar feedback on actions (the main app has a `toast()` +
  `ToastHost` pattern — an equivalent lightweight version is fine).
- **Empty, loading, and error states** for the catalog (skeleton cards while
  "loading," a real empty state for zero filter results, not just a blank grid).
- **Sold-out / upcoming / secret statuses** render distinctly (disabled buy
  CTA, countdown, or "???" treatment respectively) — don't just hide them.


### 3.3 Content
Populate at least 8–12 card entries using the real `Universe` shape.
Reuse the *existing* Nemoverse canon data as a starting point if the source
project's `data.ts` is readable (names like "THE PRIME REALITY," artists like
Aya Okafor / Kenji "KXM" Matsuda, etc.) rather than inventing an unrelated
catalog — the goal is a page that could plausibly be this brand's shop, not a
generic template. Source card art from the project's own `public/art/`
directory if you copy it in, or generate/placeholder appropriately —
just don't ship broken image paths.

## 4. Hard technical constraints


1. **Standalone project.** New directory, own `package.json`, own
   `node_modules`, own `vite.config.ts`. Zero imports reaching outside its own
   folder into `nemo-main/`. It must run with nothing but
   `npm install && npm run dev` from inside its own folder.
2. **Match the stack, don't diverge for no reason:** Vite 5.x, React 18.3.x,
   TypeScript 5.6.x strict mode, `@vitejs/plugin-react`, `framer-motion` 11.x.
   Do **not** add `three`, `gsap`, a UI kit (MUI/Chakra/shadcn), a router
   library, or a state-management library unless the feature genuinely needs
   it — the brief in §5 is about staying lean, and every dependency the main
   app doesn't already use is something a future integration has to justify.
   (React Router is a reasonable, justified exception if you implement
   deep-linkable card detail routes — a lightweight alternative like using
   the History API directly is equally acceptable.)
3. **No global-selector collisions.** The main app owns bare-tag and
   common class selectors (`body`, `.card`, `.btn`, `.shell`, `.section`,
   etc. — see `global.css`/`components.css`). Scope every shop style under a
   single root wrapper (e.g. `.nemo-shop` ancestor selector, or CSS Modules)
   so this can later be mounted inside the existing app without a single
   style bleeding in either direction. Do not restyle `html`/`body` globally
   beyond what your own root container needs.
4. **Clean mount surface.** Export one top-level `<CardShop />` component
   (default export from a single clear entry file) in addition to the normal
   standalone `main.tsx`/`index.html` entry — so integrating this later is
   "import `<CardShop />`, drop it in a route," not an archaeology project.
5. **Type-compatible data layer.** Your `Universe`/`Rarity`/`Artist` types
   must be structurally identical to §2's ground truth (same fields, same
   names) even though they're independently declared. A future merge should
   be a straight `import` swap, not a data-migration.
6. **Absolutely do not modify `nemo-main/`.** Don't edit its files, don't add
   a route/link to it, don't install anything into its `node_modules`, don't
   touch its `package.json`. This task produces a second, separate artifact.

## 5. Quality bar — this must be *better* than the main app, not a clone of its excess


The user will not be polishing this page further, while the main app is still
under active development. Treat this as the higher bar, not the lower one:


- **Leaner by design.** The main app ships two separate `three` builds
  (~365 kB + ~668 kB min) for a WebGPU black-hole simulation, a GSAP
  scroll-scrubbed "rod" rig, a custom cursor, ambient starfield canvas, and
  9,700+ lines of CSS. None of that is a rubric to hit — it's scope this page
  should deliberately not take on. A shop page should feel instant.
- **Performance budget:** aim for a production JS bundle in the low hundreds
  of kB (gzipped) for the initial route, code-split the cart/detail view if
  it helps, and target Lighthouse ≥95 Performance, ≥95 Accessibility, ≥95
  Best Practices, ≥90 SEO on a throttled mobile profile. No layout shift from
  image loading (reserve aspect ratio boxes).
- **Images:** responsive `srcset`/`sizes`, modern formats (AVIF/WebP) with a
  fallback, lazy-load everything below the fold, eager + high fetchpriority
  only for the first visible hero/featured card.
- **Accessibility:** full keyboard operability (tab through filters, cards,
  modal; Escape closes the modal and returns focus to its trigger), visible
  focus states, correct landmark/heading structure, color contrast checked
  against the dark palette above (several of the rarity accents are light-on-
  dark tinted — verify body copy never relies on accent color alone for
  meaning), `prefers-reduced-motion` fully respected.
- **Code quality:** TypeScript strict with no `any` escapes, no ESLint errors,
  no console warnings/errors at runtime, no unused dependencies.
- **Resilience:** a filter/search state that can't produce a broken UI (zero
  results is a designed state, not a blank grid); an error boundary around
  the catalog so one bad card entry can't blank the page.
- **Visual craft:** this is a premium collectibles brand — void-black canvas,
  glass panels, gradient borders, glow-based elevation (no flat drop
  shadows), rarity color-coding, tracked-uppercase metadata typography. Hit
  that bar with restraint and performance in mind, not by porting the main
  app's heaviest effects wholesale.

2. Zip the project (excluding `node_modules` and any build output) as a

   not nested inside `src/`, `public/`, or any subfolder.
4. Do **not** unzip it back into `nemo-main/`, install it there, or wire up
   any link/route/import between the two projects. Integration is a
   deliberately separate, future step.

   no integration action yourself) noting: which CSS variables/fonts it
   expects the host app to supply, where its data layer would eventually
   point at the real `lib/data.ts`, and where its wallet stub would be
   swapped for the real one — mirroring the "Production wiring" table style
   already used in `nemo-main/README.md`.

   deviations from this brief and why, and the actual Lighthouse/bundle-size
   numbers you measured.
